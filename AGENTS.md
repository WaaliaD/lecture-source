# Лекторий — планы и структура проекта

Этот файл является рабочим файлом агента проекта. В нём хранятся архитектура,
текущий план и правила обработки лекций. При изменении архитектуры сначала
обновляй этот файл.

Текущий план и правила реализации хранятся в этом файле. Отдельный файл
трекера реализации не используется.

## Цель проекта

«Лекторий» — локальный конвейер обработки лекций:

```text
MP4/аудиозапись → WAV → локальный Whisper → transcript.raw.json
             → визуальные материалы и документы
             → локальная LLM Qwen → lecture.json → lecture.md в Obsidian
```

Видео после успешной обработки можно удалить. Постоянный набор лекции:
WAV, JSON-источники, итоговый JSON, Markdown-конспект и значимые изображения.

Будущий режим для онлайн-лекций — захват без полного видео:

```text
системный звук → WAV-сегменты → объединённый audio.wav
экран          → временный анализ кадров → значимые скриншоты
                         ↓
                    единая временная шкала
```

В этом будущем режиме MP4 вообще не создаётся. Сервис захвата должен владеть обоими
потоками и проставлять событиям время на одной монотонной шкале. Для аудио
время надёжнее вычислять по индексу семпла (`sample_index / sample_rate`), а
для скриншота сохранять соответствующий timestamp capture-сервиса. Системные
часы и время изменения файлов не использовать для синхронизации.

Аудио лучше писать сегментами по 1–5 минут для защиты от потери всей записи
при сбое, а после остановки объединять их без изменения временной шкалы. Экран
анализировать с малой частотой и уменьшенным разрешением, держать небольшой
кольцевой буфер в памяти и записывать на диск только значимые кадры.

Ограничение режима: если событие не было обнаружено, восстановить визуальный
материал после лекции будет невозможно, поскольку полного видео нет. Поэтому
нужен диагностический режим с сохранением preview или полного MP4 на коротком
тестовом фрагменте.

## Структура хранилища

```text
Лекторий/
├─ AGENTS.md
├─ _context/
│  ├─ university.md       # постоянные сведения о вузе
│  ├─ vocabulary.txt      # термины, сокращения и фамилии для Whisper
│  └─ terms.md             # расшифровки и пояснения; не заменяют исходные сокращения
└─ N.N Предмет/
   ├─ _context/
   │  ├─ course.md         # постоянный контекст дисциплины
   │  ├─ lectures.md       # краткие итоги предыдущих лекций
   │  └─ terms.md          # предметные пояснения при необходимости
   └─ YYYY-MM-DD, Название лекции/
      ├─ source.wav
      ├─ transcript.raw.json
      ├─ visuals.json
      ├─ materials.json
      ├─ lecture.json
      ├─ manifest.json
      ├─ assets/
      └─ lecture.md
```

Первая цифра предмета — семестр, вторая — номер предмета. Ветка `0.x`
используется для общей учебной информации, ВКР, практики, научной работы и
многосеместровых дисциплин.

## Контексты

- `Лекторий/_context/university.md` — общий фон вуза для формирования итогового
  `lecture.json`.
- `Лекторий/_context/vocabulary.txt` — только формы слов, которые важно хорошо
  распознавать: термины, сокращения, фамилии. Их не нужно расшифровывать,
  разворачивать или заменять при работе Whisper.
- `Лекторий/_context/terms.md` — отдельный справочник расшифровок и пояснений.
- `Предмет/_context/` — память конкретной дисциплины: краткие итоги лекций,
  предметные термины и постоянные сведения курса.

## Порядок обработки лекции

1. Извлечь из MP4 нормальный WAV и проверить длительность/таймшкалу.
2. Запустить локальный Whisper, предпочтительно `large-v3-turbo`, передав
   `vocabulary.txt` в качестве словаря/подсказки.
3. Сохранить неизменённый результат ASR с минимумом `text`, `start`, `end`.
4. Извлечь из видео значимые кадры, а не каждый кадр подряд; убрать дубликаты,
   выполнить OCR/VLM и сохранить таймкод каждого материала в `visuals.json`.
5. Обработать презентацию, методичку и текстовые заметки отдельно, отдавая
   приоритет оригиналу PPTX/PDF перед OCR экрана; сохранить результат в
   `materials.json`.
6. Собрать входной пакет для Qwen: ASR, визуальные материалы, документы,
   контекст предмета, контекст вуза и справочник терминов.
7. Получить от Qwen канонический `lecture.json`: структуру, определения,
   объяснения, примеры, выводы, таймкоды, ссылки на слайды и сомнительные места.
8. Сгенерировать `lecture.md` детерминированным рендерером из `lecture.json` и
   сразу сохранить его в Obsidian vault.
9. После проверки обновить контекст предмета и при необходимости общий словарь.
10. Записать в `manifest.json` хеши входов, версии моделей и промптов. Только
    после успешной проверки удалить исходный MP4.

## Принципы

- JSON — машинный источник истины; Markdown — пользовательское представление.
- Таймкоды нельзя терять: шкала WAV и видео должна быть синхронизирована.
- Сырые данные ASR не переписывать; исправления хранить как нормализованные
  значения с указанием источника.
- Промпты ASR, извлечения материалов и суммаризации хранить отдельно и
  версионировать.
- Обрабатывать этапы с кэшем, чтобы изменение шаблона Markdown не запускало
  Whisper и LLM заново.

## Расширенные архитектурные решения из предыдущего обсуждения

Эти решения считаются утверждённой целевой архитектурой и внедряются
постепенно. Текущая раскладка лекций непосредственно в корне — временная мера;
при реорганизации проект будет разделён на три корневые директории:
`01_lectures`, `02_vault` и `03_app`.

### Жизненный цикл папки лекции

Для новой лекции желательно иметь отдельные зоны:

```text
lecture/
├─ _meta.yaml       # идентификатор, предмет, дата, время, статус
├─ source/          # временные входные файлы до завершения обработки
├─ processed/       # WAV, отрендеренные слайды и прочие промежуточные файлы
├─ json/            # результаты отдельных этапов и связи между ними
├─ chunks/          # кэш запросов LLM; временно или по флагу --keep-work
└─ audio.wav        # постоянный аудиопервоисточник
```

Markdown не хранится в папке лекции. После генерации он сразу записывается в
Obsidian vault; второй копии в «Лектории» нет. «Лекторий» остаётся
преимущественно машинным хранилищем JSON и аудио.

После успешной обработки `processed/`, `chunks/` и промежуточные JSON можно
удалять. Постоянными остаются WAV, исходные учебные материалы, TXT-заметки,
итоговый `lecture.json` и значимые изображения. Исходный MP4 хранится только на
время обработки и удаляется после проверки всех результатов. Конкретные имена
директорий могут быть адаптированы к уже существующей структуре проекта.

### JSON-слои

Полезно разделять результаты, а не складывать всё в один файл:

```text
json/
├─ sources.json
├─ transcript/
├─ presentations/
├─ documents/
├─ images/
├─ relations/
├─ lecture-context.json
└─ final/lecture.json
```

`lecture.json` — канонический результат LLM и источник для генерации Markdown.
Отдельные `relations/` могут связывать сегменты транскрипта со слайдами,
материалами курса и изображениями. Для нескольких аудиозаписей нужен также
объединённый транскрипт с сохранением исходных таймкодов и смещений.

### Общие материалы предмета

Если методичка, учебник или лабораторные относятся ко всему предмету, их можно
хранить в `Предмет/_context/materials/`:

```text
materials/
├─ source/       # оригиналы, приложение их не изменяет
└─ extracted/    # document.json/document.md, созданные один раз
```

`manifest.json` материалов должен содержать идентификатор, тип, путь, SHA-256 и
результат извлечения. Это позволяет не разбирать повторно неизменившиеся
файлы и обнаруживать замену методички.

### Содержимое `03_app/`

При реализации приложения целесообразно разделить его на:

```text
03_app/
├─ pipelines/    # orchestration этапов
├─ parsers/      # PPTX, PDF, DOCX, изображения, plaintext
├─ providers/    # FFmpeg, Whisper, Ollama text/vision, LibreOffice
├─ models/       # Pydantic-схемы данных, не модели ИИ
├─ storage/      # SQLite и repository
├─ prompts/      # версионируемые промпты
├─ templates/    # Jinja2-шаблоны Obsidian
├─ utils/
└─ tests/
```

Главный pipeline: проверка → ingest → аудио/ASR → презентации → документы →
изображения → связи → сбор контекста → chunking → суммаризация → `lecture.json`
→ Markdown → обновление контекста → очистка.

SQLite может использоваться только как служебное состояние: регистрация
источников, статусы этапов, ошибки и кэш. База не является единственным
хранилищем знаний и должна восстанавливаться из файлов лекции.

### Конфигурация и воспроизводимость

Нужны отдельные версии для промптов и шаблонов:

```text
prompts/summarization/final_v001.md
prompts/vision/slide_v001.md
templates/obsidian/lecture_v001.md.j2
```

Существенно изменённый промпт получает новую версию, старые версии не
переписываются. В `manifest.json` и итоговом JSON записываются модели, версии
промптов/шаблона, параметры запуска и SHA-256 входных файлов.

Рекомендуемые CLI-операции: `process`, `reprocess`, `parse`, `transcribe`,
`summarize`, `render`, `status`, `cleanup`. Пути должны задаваться через
конфигурацию или `LECTORY_ROOT`, а не быть зашиты в код.

## Важные расхождения, которые нужно считать разрешёнными решениями

1. Предыдущая схема из пяти корневых сущностей (`01_lectures`, `02_app`,
   `03_runtime`, `04_vault` и прочие служебные элементы) заменена на три
   директории: `01_lectures`, `02_vault`, `03_app`. Код, runtime, скрипты,
   окружение и техническая документация объединяются в `03_app`.
2. В предыдущем варианте был единый глобальный `context.md`. Текущее решение
   точнее: глобальный контекст разделён на `university.md`, `vocabulary.txt` и
   `terms.md`; контекст предмета находится только в `_context` предмета.
3. В предыдущем варианте итоговый Markdown лежал рядом с JSON внутри папки
   лекции. Текущее решение окончательное: Markdown сразу помещается в
   Obsidian vault, а в «Лектории» его копии нет.
4. В предыдущем варианте WAV считался промежуточным файлом, полученным из
   исходного M4A/MP4. Текущее решение окончательное: WAV — постоянный
   аудиопервоисточник, а MP4 — временный файл, удаляемый после проверки.
5. В предыдущем варианте предлагалось не хранить JSON в Git. Это не
   архитектурное требование текущего плана, а практическая политика хранения:
   объёмные аудио, видео и машинные артефакты следует исключать из Git, а
   правила для JSON нужно определить отдельно после первых реальных лекций.

Целевая структура корня проекта:

```text
Лекторий/
├─ 01_lectures/        # исходники, JSON, изображения, документы, презентации, контексты
├─ 02_vault/            # отдельный Obsidian vault: Markdown и связанные изображения
└─ 03_app/              # исходный код, runtime, окружение, скрипты и техдокументация
```

Во всех спорных случаях приоритет имеют более поздние решения текущего плана,
зафиксированные выше, а не старый вариант дерева.

## Obsidian vaults

Основной личный Obsidian vault и vault «Лекторий» — разные сущности. Vault
«Лекторий» физически хранится в корне проекта как `02_vault/`.

```text
Основной vault пользователя     # личные заметки, задачи, проекты, приватные связи
Лекторий vault                  # сгенерированные конспекты и учебные материалы
```

`Лекторий vault` создаётся отдельно и является целевым местом для итоговых
`lecture.md`. Внутри него хранятся только Markdown-конспекты и необходимые для
них изображения. Изображения можно копировать в vault или ссылаться на них
относительно vault, но нельзя оставлять ссылки на временные файлы из
`01_lectures`.

Это даёт несколько преимуществ:

- личная база знаний не смешивается с автоматически созданными материалами;
- конспекты можно целиком копировать, архивировать или расшаривать сокурсникам;
- можно отдельно настроить Git, синхронизацию и права доступа;
- повторение лекций можно организовать внутри специализированного vault.

Экспорт из «Лектория» в vault должен быть односторонним и воспроизводимым:

```text
Лекторий (JSON + WAV + контекст)
    → генератор Markdown
    → Лекторий vault
```

Конспекты не должны зависеть от заметок основного vault. В Markdown следует
использовать относительные ссылки, стабильные идентификаторы лекций и вложения
внутри самого vault. Нельзя оставлять ссылки на абсолютные пути компьютера,
временные файлы или приватные заметки.

Перед расшариванием нужно иметь возможность собрать публичную копию vault без:

- WAV, исходных записей и внутренних JSON;
- персональных заметок и служебного контекста;
- приватных данных о преподавателях, вузе или однокурсниках;
- внутренних путей, логов и технических метаданных.

Публичный набор лучше формировать экспортом или фильтрацией, а не ручным
копированием отдельных заметок. Так можно будет повторно собрать его после
перегенерации конспектов.

## Актуальная спецификация проекта

Этот раздел уточняет и заменяет более ранние наброски выше. В случае
расхождения использовать именно его.

### Корневая структура

В итоговом проекте используются только три основные директории:

```text
Лекторий/
├─ 01_lectures/   # исходники, WAV, JSON, изображения, документы, презентации и контексты
├─ 02_vault/      # отдельный Obsidian vault: только MD и нужные изображения
└─ 03_app/        # весь код, runtime, окружение, скрипты и технические материалы
```

Текущие предметные папки в корне — временная мера. При реорганизации их нужно
перенести в `01_lectures/`. Не создавать отдельные корневые `02_app`,
`03_runtime` или `04_vault`.

### `01_lectures/`: машинное хранилище

```text
01_lectures/
├─ _context/
│  ├─ university.md
│  ├─ vocabulary.txt
│  └─ terms.md
├─ 0-1_Общее/
├─ 1-1_Название-предмета/
│  ├─ _meta.yaml
│  ├─ _context/
│  │  ├─ course.md
│  │  ├─ lectures-summary.md
│  │  ├─ terms.md
│  │  └─ materials/
│  │     ├─ source/
│  │     └─ extracted/
│  └─ YYYY-MM-DD_HH-mm/
└─ ...
```

`01_lectures/<subject>/_meta.yaml` — постоянные метаданные предмета. Они
используются для автоматического заполнения лекций и выбора контекста курса.
Метаданные конкретной лекции находятся в её собственной папке.

Ветка `0.x` предназначена для общей учебной информации, ВКР, практики,
научной работы и многосеместровых сущностей. Первая цифра предмета — семестр,
вторая — порядковый номер.

Папка лекции:

```text
YYYY-MM-DD_HH-mm/
├─ _meta.yaml
├─ source/                  # постоянные источники: WAV, скриншоты и документы
├─ processed/               # временные конвертации, рендеры и кадры
├─ json/
│  ├─ sources.json
│  ├─ transcript.json
│  ├─ presentation.json
│  ├─ documents.json
│  ├─ visuals.json
│  ├─ relations.json
│  └─ context.json
├─ 1-1_YYYY-MM-DD_HH-mm.json # итоговый результат лекции
├─ chunks/                  # входы/выходы LLM для отладки
└─ manifest.json
```

Markdown в `01_lectures` не хранится. MP4 удаляется после успешной проверки;
source/WAV, JSON и необходимые изображения сохраняются. `processed/` и `chunks/`
удаляются после успеха, если не включён режим сохранения отладки.

### `02_vault/`: пользовательский результат

`02_vault` — самостоятельный Obsidian vault, не личный основной vault.
Приложение записывает туда Markdown сразу после генерации:

```text
02_vault/
├─ 0.1_Общее/
├─ 1-1_Название-предмета/
│  ├─ 2026-09-13 Название лекции.md
│  └─ assets/
└─ ...
```

Внутри только Markdown и изображения, на которые ссылаются конспекты. Изображения
из `01_lectures` можно копировать в `02_vault/assets/`; ссылки должны быть
относительными и работать после передачи vault другому человеку. Не ссылаться
на абсолютные пути, MP4, WAV, JSON, временные каталоги или личные заметки.

Экспорт односторонний:

```text
01_lectures/1-1_Название-предмета/YYYY-MM-DD_HH-mm/*.json
  → шаблон в 03_app
  → 02_vault/*.md
```

Глобальный скрипт `03_app/scripts/08_publish_vault.py` сканирует весь
`01_lectures`, копирует только лекционные Markdown с YAML frontmatter в
`02_vault`, переносит связанные изображения и обновляет индекс сайта.
`03_app/scripts/09_publish_github.py` запускает этот экспорт, создаёт коммит
и отправляет его в настроенный Git remote по флагу `--push`. Workflow
`.github/workflows/pages.yml` собирает `02_vault` через Jekyll и публикует его
на GitHub Pages.

Публичная копия vault должна собираться автоматически с фильтрацией WAV, JSON,
служебного контекста, персональных данных, логов и внутренних путей.

### `03_app/`: приложение и техническая часть

```text
03_app/
├─ main.py
├─ pyproject.toml
```

`runtime/` включает whisper-cli и модели Whisper, Ollama и список моделей,

не коммитится; пути не зашиваются в код, используется конфигурация или
`LECTORY_ROOT`.

### Полный порядок обработки

1. **Ingest**: принять MP4/аудио, презентации, документы, изображения и
   заметки; создать метаданные, SHA-256 и `sources.json`.
2. **Audio**: извлечь WAV, проверить длительность и временную шкалу.
3. **ASR**: запустить локальный Whisper `large-v3-turbo` с
   `vocabulary.txt`; сохранить неизменённый `raw.json` с `text`, `start`,
   `end`. Для нескольких аудио сохранить исходный файл и временное смещение.
4. **Presentations**: разобрать PPTX/PDF; извлечь текст, заголовки, таблицы,
   заметки, номера слайдов и изображения. Оригинальный текстовый слой важнее
   OCR; слайды при необходимости отрендерить и передать vision-модели.
5. **Documents**: отдельно разобрать PDF, DOCX, TXT и MD; общие материалы
   предмета извлечь один раз в `_context/materials/extracted/`.
6. **Visuals**: извлечь значимые кадры по смене слайда/сцены, удалить
   дубликаты, выполнить OCR/VLM и сохранить `timestamp` каждого кадра. Для
   вручную сохранённых скриншотов шаг 13 связывает их с видео по времени в
   именах файлов и формирует отдельные таймкоды для каждого видео.
7. **Alignment**: связать речь, слайды, кадры и документы по времени, порядку
   и при необходимости семантическому сходству.
8. **Context**: собрать общий вузовский контекст, словарь, расшифровки,
   контекст предмета и релевантные материалы в `lecture-context.json`.
9. **Chunking**: разделить длинную лекцию на смысловые блоки с локальным
   контекстом; сохранять вход и выход каждого блока.
10. **Qwen**: шаг 15 формирует независимые чанки из всех доступных источников,
    шаг 16 обрабатывает их Qwen и объединяет в канонический `lecture.json`.
11. **Render**: без дополнительного LLM-запроса отрендерить JSON в Markdown и
    записать результат в `02_vault`.
12. **Update context**: добавить краткий итог лекции в
    `lectures-summary.md`, при необходимости обновить словарь и контекст.
13. **Validate**: проверить JSON-схему, таймкоды, изображения, ссылки,
    Markdown и manifest.
14. **Cleanup**: только после успеха удалить MP4, `processed/` и `chunks/`.

### Контексты

`01_lectures/_context/university.md` — постоянные сведения вуза для Qwen.
`vocabulary.txt` — только формы слов для Whisper: термины, сокращения,
фамилии, организации и названия программ. Сокращения не расшифровывать.
`terms.md` — отдельные расшифровки и пояснения; исходное сокращение в выводе
сохранять.

Контекст предмета находится только в `_context` соответствующего предмета:
`course.md`, `lectures-summary.md`, предметный `terms.md` и общие материалы.
Передавать нужно компактную память, а не полные старые лекции. Ручные разделы
не изменять молча; AI-обновления должны быть легко проверяемы через diff.

### Файлы и директории одной лекции

Назначение каждого элемента папки лекции:

- `source/` — постоянная папка первоисточников: нормализованный WAV,
  презентации, документы, заметки и значимые скриншоты. MP4 временно находится
  здесь и удаляется после успешной проверки.
- `processed/` — временные технические результаты: фрагменты WAV, поток
  анализируемых кадров, отрендеренные страницы/слайды и промежуточные OCR-файлы.
  Может быть удалён после успешной обработки; сохраняется только если нужен
  debug. Полный набор кадров видео здесь не архивируется.
- `json/` — объединённые результаты отдельных этапов: транскрипт, презентации,
  документы, изображения, связи и контекст. Итоговый JSON хранится в корне
  папки лекции и называется по предмету и дате.
- `chunks/` — точные входы и ответы Qwen по смысловым блокам. Это кэш и
  диагностический материал, а не окончательный источник истины; удаляется после
  успеха, если не включён `--keep-work`.
- Значимые изображения хранятся в `source/`: финальное состояние слайда перед
  сменой, схемы, графики и важные кадры. При экспорте выбранные файлы
  копируются в `02_vault/assets/`.
- `manifest.json` — паспорт обработки: список входов и их SHA-256, статусы
  этапов, версии моделей/промптов/шаблона, параметры запуска, пути результатов,
  время обработки, смещения временных шкал и сведения о cleanup.

Правило хранения видео: после обработки видео не сохраняется. Постоянными
визуальными результатами являются только отобранные лёгкие скриншоты, которые
нужны для понимания лекции и Markdown-конспекта.

#### Алгоритм отбора скриншотов

Программа не сохраняет кадр через фиксированный интервал и не реагирует на
каждый штрих преподавателя. Она работает как конечный автомат:

1. Анализирует видео с небольшой частотой и уменьшенным разрешением; полный
   поток кадров используется только временно.
2. Для текущего слайда хранит небольшой кольцевой буфер последних стабильных
   кадров.
3. Сравнивает кадры по глобальному изменению изображения: perceptual hash,
   SSIM/разнице блоков и, при необходимости, признакам OCR/vision. Небольшое
   локальное изменение считается пометкой, а не сменой слайда.
4. При обнаружении крупной смены слайда ждёт окончания перехода и подтверждает,
   что новый кадр стабилен несколько последовательных измерений.
5. Перед подтверждённой сменой сохраняет последний стабильный кадр старого
   слайда из буфера. Поэтому в нём остаются все накопленные пометки, но не
   сохраняется каждый промежуточный штрих.
6. Новый слайд начинает отслеживаться с первого стабильного кадра. Отдельный
   кадр нового слайда сохраняется только если он нужен для связи с презентацией
   или если оригинальная презентация недоступна.
7. В конце видео сохраняет последний стабильный кадр текущего слайда.

Для каждого сохранённого изображения записываются `timestamp`, длительность
состояния слайда, источник видео, номер/ID слайда, причина сохранения и путь к
файлу. Порог крупного изменения, длительность стабилизации и запас времени до
перехода должны быть параметрами конфигурации, а не зашиваться в код.

Если преподаватель долго пишет на одном слайде, промежуточные состояния не
сохраняются: итоговый кадр попадёт в буфер и будет выбран перед следующей
крупной сменой или в конце лекции. Если на слайде есть анимация или прокрутка,
это нужно отдельно помечать как особый режим, поскольку простого сравнения
кадров может быть недостаточно.

В папке лекции не создаётся Markdown. Итоговый Markdown находится только в
`02_vault`.

Помимо WAV и изображений в `01_lectures` могут находиться следующие файлы:

- `lecture.json` — постоянный итоговый машинный результат. Сырой транскрипт,
  анализ презентаций и документов, OCR, связи и собранный контекст могут
  временно храниться в `json/` для сборки, но после успеха удаляются, если не
  нужны для отладки или повторной обработки;
- `_meta.yaml` — постоянные метаданные лекции;
- `manifest.json` — постоянный паспорт входов и обработки;
- презентации, методички, PDF/DOCX, TXT-заметки и исходные изображения —
  сохраняемые первоисточники лекции;
- извлечённые представления документов и презентаций — промежуточные JSON/MD
  для машинного использования, но не пользовательский конспект;
- временные chunk-запросы и промежуточные файлы — только для кэша и отладки,
  удаляются после успеха.

Таким образом, после успешной обработки в `01_lectures` постоянно остаются:

- `source/audio.wav`;
- презентации и методички;
- TXT-заметки;
- значимые скриншоты/изображения лекции;
- итоговый `lecture.json`;
- служебные `_meta.yaml` и `manifest.json`.

Исходный MP4, временные конвертации, отрендеренные дубликаты, chunk-кэш и
прочие промежуточные файлы удаляются после успешной проверки.

Таким образом, `01_lectures` хранит не только аудио и картинки, но и
структурированное машинное описание лекции. `02_vault` хранит только итоговый
Markdown и изображения, встроенные в него. Тяжёлые исходные видео, WAV,
внутренние JSON и служебные файлы в vault не копируются.

#### `_meta.yaml`

`_meta.yaml` внутри папки лекции — короткие человекоредактируемые метаданные,
не результат LLM. Минимальный состав:

```yaml
id: "1-1_2026-09-13_16-00"
course_id: "1-1"
course_name: "Название предмета"
title: "Название лекции"
date: "2026-09-13"
time: "16:00"
lecture_number: 1
semester: 1
lecturer: null
status: "new"
vault_note: "1-1_Название-предмета/2026-09-13 Название лекции.md"
```

Для предмета в его корневом `_meta.yaml` хранится `subject_number` — порядковый
номер предмета внутри семестра. Для лекции хранится `lecture_number` — её
порядковый номер в рамках предмета. Оба значения назначаются автоматически при
создании и не должны зависеть от переименования папки или заголовка.

Статусы лекции:

- `new` — папка создана, исходные файлы ещё не приняты;
- `ingested` — входы зарегистрированы, типы файлов и SHA-256 рассчитаны;
- `transcribed` — WAV подготовлен и сырой транскрипт сохранён;
- `enriched` — обработаны презентации, документы, изображения и связи;
- `summarized` — собран итоговый `lecture.json`;
- `rendered` — Markdown записан в `02_vault`;
- `validated` — проверены JSON, таймкоды, изображения, ссылки и Markdown;
- `completed` — обработка завершена, разрешена очистка временных данных;
- `failed` — этап завершился ошибкой; входы и диагностические данные сохраняются.

Переходы обычно идут последовательно: `new` → `ingested` → `transcribed` →
`enriched` → `summarized` → `rendered` → `validated` → `completed`. При ошибке
любой этап может перейти в `failed`; после исправления обработка продолжается
с последнего успешно завершённого этапа. Идентификатор должен оставаться
стабильным при переименовании заголовка лекции.

#### `lecture.json`

`lecture.json` — валидируемый канонический результат интеллектуальной обработки,
а не просто summary. Он должен описывать содержание лекции и происхождение
утверждений:

```json
{
  "id": "1-1_2026-09-13_16-00",
  "title": "Название лекции",
  "summary": "Краткое содержание",
  "topics": ["Тема 1"],
  "sections": [
    {
      "id": "section-01",
      "title": "Раздел",
      "time_start": 120.0,
      "time_end": 900.0,
      "items": [
        {
          "type": "definition",
          "text": "...",
          "time_start": 240.0,
          "time_end": 280.0,
          "sources": ["transcript:segment-12", "slide:4"],
          "images": ["assets/frame-00240.jpg"],
          "confidence": "high"
        }
      ]
    }
  ],
  "key_terms": [],
  "examples": [],
  "teacher_notes": [],
  "conclusions": [],
  "tasks": [],
  "uncertainties": [],
  "generation": {
    "asr_model": "large-v3-turbo",
    "llm_model": "qwen3:14b",
    "prompt_versions": {},
    "template_version": "lecture_v001",
    "generated_at": "2026-09-13T16:00:00+05:00"
  }
}
```

Обязательные смысловые поля: `id`, `title`, `summary`, `sections` и
`generation`. Для каждого важного элемента желательно иметь таймкод и ссылку
на исходный сегмент, слайд, документ или изображение. Дополнительные поля:
`topics`, `key_terms`, `examples`, `teacher_notes`, `conclusions`, `tasks` и
`uncertainties` могут быть пустыми массивами.

`lecture.json` используется рендерером для создания Markdown и может быть
пересобран без повторного запуска Whisper. Markdown не должен быть отдельным
результатом свободной генерации Qwen.

Транскрипт:

```json
{"id": 0, "start": 12.4, "end": 18.9, "text": "текст"}
```

Визуальный объект:

```json
{
  "id": "frame-00843",
  "timestamp": 842.7,
  "path": "assets/frame-00843.jpg",
  "ocr": "текст на экране",
  "description": "описание схемы",
  "source": "lecture.mp4"
}
```

`lecture.json` должен содержать как минимум `id`, `title`, `summary` и
`sections`. Остальные разделы, включая источники, таймкоды, изображения,
термины и сомнения, добавляются по мере наличия данных и возможностей
конкретного обработчика. Это источник истины для Markdown. LLM не должна
додумывать факты; сомнения и конфликты источников явно помечаются.

### Источники и приоритеты

Обычно приоритет такой: речь преподавателя → оригинальная презентация или
документ → OCR/VLM → контекст → предположение модели. При конфликте нельзя
молча скрывать расхождение. Для нормализации ASR по возможности хранить
`raw`, `normalized`, источник и confidence.

### Промпты и воспроизводимость

Промпты живут в `03_app/prompts/` и не зашиваются в код:

```text
prompts/asr/
prompts/vision/slide_v001.md
prompts/documents/analyze_v001.md
prompts/summarization/chunk_v001.md
prompts/summarization/final_v001.md
prompts/context/course-update_v001.md
templates/obsidian/lecture_v001.md.j2
```

Существенное изменение получает новую версию; старые промпты не переписывать.
В `manifest.json` фиксировать модели, промпты, шаблон, параметры, дату и хеши
входов. Изменение шаблона не должно повторно запускать Whisper или Qwen.

### Служебное состояние и команды

SQLite — только служебное состояние: источники, статусы, ошибки и кэш. Файлы
лекций остаются основным хранилищем и должны позволять восстановить БД.

Минимальный CLI: `process`, `parse`, `transcribe`, `summarize`, `render`,
`reprocess`, `status`, `cleanup`. Полный pipeline: validate → ingest → audio
→ ASR → presentations → documents → visuals → alignment → context → chunking
→ Qwen → lecture.json → render → update context → validate → cleanup.

### Git и критерии успешной обработки

В Git хранить код, промпты, шаблоны, документацию, схемы, default-конфигурацию
и ручные контексты. Не хранить MP4, WAV, большие исходники, модели, бинарники,
SQLite и логи. Для JSON решение принять после первых реальных лекций с учётом
размера и ценности истории изменений.

Удаление разрешено только когда одновременно существует валидный
`source/audio.wav`,
JSON, `02_vault`-Markdown, доступные изображения, обновлённый контекст и
заполненный `manifest.json`. При ошибке сохранять входы и кэш.

## Утверждённая структура `03_app`

Техническая часть проекта организуется по ролям:

```text
03_app/
├─ application/       # исходный код приложения
├─ infrastructure/    # FFmpeg, Whisper, Ollama, конфигурация запуска
├─ operations/        # установка, диагностика, backup, cleanup
├─ resources/         # prompts, templates, JSON schemas
├─ tests/             # unit и integration tests
├─ docs/              # техническая документация
└─ state/             # SQLite, cache, logs; не источник учебных данных
```

### Содержимое `application/`

Здесь находится только исходный код и описание Python-проекта — без моделей,
бинарников, логов и лекционных данных:

```text
application/
├─ lectory/
│  ├─ __main__.py             # запуск приложения как Python-модуля
│  ├─ cli/                    # команды process, parse, transcribe и т. д.
│  ├─ pipelines/              # orchestration этапов обработки лекции
│  ├─ parsers/                # PPTX, PDF, DOCX, image, TXT/MD
│  ├─ providers/              # интерфейсы FFmpeg, Whisper, Ollama, LibreOffice
│  ├─ models/                 # Pydantic-схемы и модели данных
│  ├─ services/               # context, alignment, chunking и бизнес-логика
│  ├─ storage/                # repository и доступ к служебному состоянию
│  └─ utils/                  # пути, хеши, время, ошибки, логирование
├─ pyproject.toml             # зависимости и настройки Python-пакета
└─ README.md                  # запуск и разработка приложения
```

Ответственность модулей:

- `cli` принимает команды и параметры, но не реализует обработку напрямую;
- `pipelines` задаёт порядок и статусы этапов;
- `parsers` извлекает данные из форматов и не вызывает LLM;
- `providers` скрывает конкретные CLI/API Whisper, Ollama и внешних инструментов;
- `models` задаёт единые схемы данных для всех этапов;
- `services` выполняет нормализацию, сбор контекста, связи и chunking;
- `storage` работает только со служебным состоянием, а не заменяет файлы
  `01_lectures`;
- `utils` содержит общие технические функции.

### Остальные директории `03_app`

- `infrastructure/` — manifest окружения, настройки запуска и описания путей;
  portable FFmpeg, Whisper и другие бинарники. Модели и бинарники исключаются
  из Git.
- `operations/` — PowerShell-скрипты установки, проверки окружения,
  benchmark, backup и безопасной очистки.
- `resources/` — версионируемые промпты, Jinja2-шаблоны Obsidian и JSON-схемы.
- `tests/` — короткие fixtures, unit-тесты и интеграционные тесты pipeline.
- `docs/` — архитектура, pipeline, установка, модели, промпты и troubleshooting.
- `state/` — SQLite, кэш и логи выполнения; это не постоянное хранилище знаний
  и директория может быть восстановлена или очищена.

Разработка тестов пока отложена до появления основного offline-конвейера.
Никакие существующие или новые автоматизированные тесты на текущем этапе не
запускать и не добавлять.

### Текущее решение по форме приложения

Проект реализуется не как большое монолитное приложение, а как набор
небольших независимых скриптов. Скрипты последовательно выполняют этапы
pipeline и обмениваются файлами внутри папки лекции: `sources.json`, JSON
результатами отдельных этапов, `manifest.json` и итоговым `lecture.json`.

Общий CLI, сложная внутренняя архитектура пакета и SQLite не являются
обязательными условиями текущего этапа. Их можно добавить позднее, если набор
скриптов станет неудобно запускать или сопровождать. Каждый новый скрипт должен
по возможности иметь одну ответственность, принимать пути и параметры через
аргументы или конфигурацию и быть пригодным для ручного запуска.

### Текущая политика тестирования

Пока не делать никаких тестов вообще: не создавать unit-тесты,
integration-тесты, test suite и отдельные тестовые fixtures. Проверка работы
выполняется только внутри специального предмета `01_lectures/0-0_Тесты`.
Рабочие предметы для тестов и пробных запусков не использовать. Тестирование
будет выделено в отдельную задачу после сборки основного offline-конвейера.

Все тесты и пробные запуски — автоматизированные и ручные — проводить только
на предмете `0-0_Тесты`. Если этого предмета нет, сначала создать его.

### Комментарии в коде

В коде проекта комментарии не добавлять. Назначение и порядок работы скриптов
описывать в `03_app/scripts.md`, `03_app/README.md` или другой технической
документации.

### Оформление `03_app/scripts.md`

Для каждого скрипта в `scripts.md` использовать нумерованный список. В
заголовке указывать только название скрипта, без пути и расширения файла. После
заголовка писать краткое описание одной строкой, затем сразу команду запуска.
Отдельную строку «Запуск на `0-0_Тесты`» не добавлять.

### Лёгкий вариант конвейера в `03_app`

`03_app/` — самостоятельный минимальный набор ручных скриптов поверх
существующего runtime Whisper в `03_app/whisper`. Он не заменяет полный
конвейер `03_app` и не меняет его файлы. В lightweight-потоке метаданные
лекции хранятся в корне лекции: `lecture/_meta.yaml`.

Порядок шагов: `00_run_pipeline`, `01_create_lecture_meta`, `02_bind_video_screenshots`,
`03_extract_audio`, `04_transcribe_turbo`, `05_extract_pdf`,
`06_merge_lecture_data`. До шага 02 видео и скриншоты
лежат непосредственно в корне папки лекции; после шага видео находятся в
`source/`, скриншоты — в `source/fragments/`. WAV создаётся в `source/` с
базовым именем исходника. Сырые транскрипции сохраняются непосредственно в
`transcript/`, объединённый файл — `json/transcript.json`, PDF-материалы —
`json/pdf.json`, итоговый объединённый JSON — в корне лекции. Whisper использует только
`01_lectures/<subject>/_context/vocabulary.txt` текущего предмета, если он
существует; при отсутствии Whisper работает без подсказки. Общий словарь из
`01_lectures/_context/` для lightweight-потока не используется. Для запуска
достаточно видео или аудио; PDF и скриншоты являются необязательными входами.
Шаг 06 не использует LLM и не строит семантические связи: он объединяет
исходную транскрипцию, тайминги, имена и OCR скриншотов, а также `pdf.json`.
`00_run_pipeline` перед запуском проверяет окружение и перехватывает ошибки
дочерних скриптов, чтобы вместо traceback выводить список проблем и код выхода.
